**3. 발견한 버그·위험**

**B01 — 작업·방문 상태 전이 검증 누락: 코드상 확인, P0**

- `changeJobStatus`는 `id,version`만 읽고 모든 enum 상태를 저장합니다: `lib/jobs/service.ts:56–57`.
- `saveJob` 편집 경로도 기존 상태를 조회하지 않고 입력 상태를 저장합니다: `:38–41`.
- `changeVisitStatus`는 supervisor의 `cancelled`만 막고 완료·취소 상태에서의 역전이를 검사하지 않습니다: `lib/schedule/service.ts:43–45`.
- DB 트리거는 수정 가능한 **열**만 제한하며 전이는 검사하지 않습니다: `20261015221406_ems_scope_checks.sql:18–26`.

제안:

- supervisor: 배정된 비종료 Job/Visit을 `in_progress` 또는 `completed`로 변경 가능.
- 완료·취소 상태 재개방은 admin 전용 별도 명령과 사유 필요.
- Job 보관 상태에서는 supervisor 변경 불가.
- admin 일반 편집과 상태 명령도 같은 도메인 전이 검증을 사용.
- 기존 테스트가 허용하는 `scheduled → completed` 직접 완료는 유지합니다.

**B02 — 마지막 방문 취소·이동 후 미예약 작업 누락: 코드상 확인, P1**

`saveVisit`는 Job을 `unscheduled → scheduled`로만 변경합니다. 취소·다른 Job으로 이동할 때 이전 Job을 재평가하지 않습니다. `unscheduledJobs`는 저장 상태가 `unscheduled`인 Job만 가져옵니다.

근거: `lib/schedule/service.ts:25–35`, `:40–45`, `:59`.

따라서 마지막 유효 방문이 사라져도 Job이 `scheduled`로 남아 미예약 목록에서 빠질 수 있습니다. admin 일정 변경 시 이전·새 Job을 모두 재평가해야 합니다. `in_progress/completed` Job은 자동으로 되돌리지 않습니다.

**B03 — 평가 일정과 요청 파이프라인의 기준 불일치: 코드상 확인, P1**

- 요청 저장은 `assessment_at`만 바꾸며 Visit이나 배정을 생성하지 않습니다: `requests/service.ts:38–41`.
- 일정 저장은 Visit을 바꾸며 해당 필드를 갱신하지 않습니다: `schedule/service.ts:31–36`.
- 직접 Job 생성은 요청 연결만 저장하고 요청 상태를 변경하지 않습니다: `jobs/service.ts:48–50`.
- Home은 단순히 `requests.status='new'`를 셉니다: `home/service.ts:19`.

실제 방문·Job이 생긴 요청도 “새 요청”으로 남을 수 있습니다. 새 조회 모델에서 업무 단계와 일정 상태를 실제 연결 레코드로 계산해야 합니다.

**B04 — 취소 청구서 잔액의 서비스·출력 불일치: 코드상 확인, P1**

청구 서비스는 `void`도 `total - payments`를 `balance`로 반환하지만, 출력 문서는 `void` 잔액을 `0.00`으로 반환합니다.

근거: `lib/invoices/service.ts:108–109`, `:122`; `lib/documents/project.ts:20`.

새 계약에서는 다음을 구분하는 것이 안전합니다.

- `total`: 취소 후에도 보존되는 문서 금액.
- `balance`: 발행 상태일 때만 회수 대상 잔액, draft/void는 `0.00`.
- 필요하면 `nominalBalance`: 수학적인 `total - validPayments`를 별도 제공.

현재 Home은 issued만 집계하므로, **현재 Home에 void 금액이 포함된다고 판단한 것은 아닙니다.**

**B05 — 비용 상세의 전체 목록 조회: 코드상 확인, P1**

`readExpense(id)`가 전체 비용 목록을 읽고 메모리에서 `find`합니다. 목록에도 LIMIT이 없습니다.

근거: `lib/expenses/service.ts:46–50`.

페이지네이션을 추가한 뒤 이 구현을 그대로 두면 두 번째 페이지 이후 상세가 사라집니다. 상세 조회를 반드시 별도 ID 쿼리로 변경해야 합니다.

**B06 — 감사 기록의 조회·내용·불변성 부족: 코드상 확인, P1**

- 고객·비용 수정 이벤트는 대부분 빈 `data`입니다: `clients/service.ts:37`, `expenses/service.ts:33`.
- 견적 발행으로 요청 상태를 변경해도 요청 이벤트가 없습니다: `quotes/service.ts:121–122`.
- 방문 저장으로 Job 상태를 변경해도 Job 이벤트가 없습니다: `schedule/service.ts:35–36`.
- 회사 정보 저장에는 `recordActivity` 호출이 없습니다: `settings/service.ts:17–20`.
- `authenticated`에 활동 테이블 UPDATE/DELETE 권한이 있고 admin_all 정책도 적용됩니다: `20261015220541_ems_runtime.sql:8`, `:35–36`.

현재 앱에 감사 삭제 기능은 확인되지 않았습니다. 다만 감사 원본의 append-only 성질은 DB에서 보장되지 않습니다.

**B07 — 타이머·승인 재시도가 성공 결과를 복원하지 못함: 코드상 확인, P1**

중복 타이머 생성 자체는 잠금·제약으로 방지합니다. 그러나 시작과 일괄 승인에는 `runCommand`가 없어 성공 응답 유실 후 재시도가 충돌로 끝납니다.

근거: `timesheets/service.ts:42–49`, `:64–81`. 기존 동시 시작 테스트도 성공 1건·실패 1건을 기대합니다: `tests/integration/expenses-timesheets.test.ts:108–115`.

**B08 — 집계 성능·동시 조회 일관성: 잠재 위험, 미측정**

- 여러 목록은 count와 rows를 별도 SQL로 읽습니다. 기본 `BEGIN`은 두 문장 사이의 변경을 동일 스냅샷으로 고정하지 않습니다: `db/transaction.ts:26`, `clients/service.ts:77–78`.
- 청구 목록은 payment 집계를 count·rows에서 각각 사용하지만, migrations에는 `payments(organization_id,invoice_id)` 보조 인덱스가 없습니다: `invoices/service.ts:119–122`, core migration `:69–88`.
- 고객 상세는 연결 목록을 100건으로 잘라 다음 페이지나 총건수를 주지 않습니다: `clients/service.ts:89–90`.

목록 조회에서 애플리케이션이 행마다 서비스를 호출하는 전형적인 N+1은 확인하지 못했습니다. SQL 상관 서브쿼리와 무제한 조회를 성능 위험으로 구분합니다.

**오류로 분류하지 않은 동작**

- 새 초안이 생긴 뒤에도 이전 승인 revision을 Job으로 전환하는 동작은 의도된 회귀 계약입니다: `tests/integration/jobs-invoices.test.ts:93–100`, `:145–157`.
- Job의 `notes`는 현장 직원에게 공개하는 Site notes로 명시되어 있습니다: `components/jobs/job-form.tsx:26`.
- 현재 읽은 서비스에서 supervisor에게 계약·청구 금액이 실제 유출되는 경로는 확인하지 못했습니다. 새 조회·활동 기능에서 유지해야 할 권한 경계로 기록합니다.

**4. UI 변경 1~5별 서비스 설계**

아래 타입·함수는 **제안 계약**입니다. 기존 API를 바로 깨뜨리지 않도록 신규 조회 함수를 추가하고, 팀장이 화면을 전환한 뒤 중복 경로를 정리합니다.

공통 원칙:

- 조직·역할·사용자 ID는 요청 입력이 아니라 `tx.actor`에서 가져옵니다.
- 모든 SQL에 명시적인 `organization_id` 조건을 사용하고 기존 RLS도 유지합니다.
- 금액은 SQL `numeric`과 `Money = string`. JSON에 넣을 때도 `::text`로 변환합니다.
- supervisor의 고객 청구 금액은 필드를 제거한 판별 유니언으로 반환합니다. 본인 비용 금액은 기존 권한대로 허용합니다.
- 금융 목록·정렬·필터 자체가 admin 전용이면 `FORBIDDEN`을 반환합니다. 금액 0이나 빈 목록으로 위장하지 않습니다.
- 여러 쿼리로 만드는 목록·요약은 읽기 전용 repeatable-read 트랜잭션을 사용합니다.
- 날짜 판정은 한 번 얻은 `asOf`와 Sydney 현지 `today`를 공유합니다.

RLS는 행 접근을 제한하므로 금액 필드 분리는 서비스에서 함께 수행해야 합니다. 새 view로 우회하지 않고 현재 사용자 권한으로 실행합니다. [Supabase RLS 공식 문서](https://supabase.com/docs/guides/database/postgres/row-level-security)

추가 의미 규칙:

- 탭 배지는 검색·기간·고객 조건을 적용하되 **현재 선택한 탭 조건은 제외**하고 계산합니다.
- `All`은 해당 공통 조건의 전체입니다. 보관 탭이 있는 도메인은 보관 레코드도 포함합니다. 기존 API의 active 기본값은 유지합니다.
- `requires_invoicing`, `outstanding`, `overdue`, assessment 관련 탭은 중첩될 수 있습니다. 배지 합을 All과 비교하지 않습니다.
- 날짜 범위는 Clients/Requests/Quotes는 생성일, Jobs는 생성일, Invoices는 발행일, Expenses는 지출일을 기본으로 명시합니다. 만기일·방문일 필터는 별도 키로 확장합니다.
- Clients/Requests/Expenses에는 현재 업무 번호가 없습니다. `number: null`로 반환하고 번호 열을 억지로 채우지 않습니다.
- 요청은 금액 자체가 없으므로 `not_applicable`. 연결 견적 여러 건의 합계를 요청 금액으로 표시하지 않습니다.
- 새 견적 초안이 있으면 이전 revision이 전환되었더라도 현재 행은 Draft입니다. Jobber의 “Converted가 영구 최종 상태” 규칙을 EMS revision 모델에 그대로 이식하지 않습니다. [Jobber 견적 상태](https://help.getjobber.com/en/articles/quote-list-page-and-key-metrics/)

`readJobPipeline`의 금융 부분은 admin 전용입니다. supervisor Home에서는 별도의 운영 건수 쿼리만 실행하고 `job_contracts/invoices`를 조회하지 않습니다.

| 카드 | 확정할 집계 의미 |
|---|---|
| 새 요청 | 미보관·미종료이며 실제 assessment나 발행 견적·연결 Job이 없는 접수 단계 요청 |
| 평가 예정 | 미종료 요청 중 scheduled/in_progress assessment Visit가 있는 요청 수. 여러 방문이어도 요청 한 건 |
| 평가 연체 | 미완료 assessment의 종료 시각이 지남. 종일은 Sydney의 `end_date + 1` 자정 기준 |
| 승인 대기 견적 | 현재 표시 상태 awaiting_response. 현재 revision 금액 |
| 승인됨 견적 | 현재 revision 승인, 해당 revision에 연결 Job 없음 |
| 진행 중 Job | `status='in_progress' AND archived_at IS NULL`. unscheduled/scheduled를 포함하는 기존 active_jobs와 구분 |
| 청구 필요 Job | completed·미보관·non-void invoice 없음. 금액은 고정 job_contracts.total |
| 미납 Invoice | issued이며 유효 수금 차감 잔액 > 0. 부분납 포함 |
| 연체 Invoice | 미납 중 due_on < Sydney today. 금액은 원 청구액이 아닌 남은 잔액 |

계약이 없는 Job은 금액을 0으로 가장하지 않습니다. `missingAmountCount`로 드러내며, 카드 건수와 금액 집계의 불완전성을 구분합니다.

각 카드의 이동 필터는 해당 목록 탭과 동일해야 합니다. Jobber의 청구 필요 상태는 청구 알림·청구 주기에도 영향을 받지만, 이번 EMS는 승인된 전액 청구 모델의 위 정의를 유지합니다. [Jobber 작업 청구 흐름](https://help.getjobber.com/en/articles/job-basics/)

```ts
        visibility: "summary";
        changedFields: string[];
      };
  detailAvailable: boolean;
};

type ActivityPage = {
  items: ActivityItem[];
  nextCursor: { createdAt: string; id: string } | null;
};

function listActivity(
  input: ActivityInput
): Promise<Result<ActivityPage>>;
```

설계:

- admin은 기존 `activity_events`를 읽되, 이벤트별 허용 필드만 반환합니다. 계산 스냅샷 전체를 타임라인 payload에 넣지 않습니다.
- supervisor는 아래 SQL의 **안전한 요약 테이블**만 읽습니다. 원본 `data`의 RLS를 넓히지 않습니다.
- 요약에는 행위자·시각·대상·안전한 동작·변경 필드명만 저장합니다. 금액·메모 값·quoteId·청구 데이터는 복사하지 않습니다.
- `recordActivity`가 같은 트랜잭션에서 원본과 요약을 기록합니다.
- 부모 상태 자동 변경도 해당 부모 이벤트를 남깁니다.
- 과거 빈 `data`는 `detailAvailable:false`로 표시합니다. 과거 변경 전후 값을 복원했다고 주장하지 않습니다.
- `created_at DESC, id DESC`와 동일한 복합 cursor로 페이지를 나눕니다.
- client/workflow scope는 관계 대상 집합을 먼저 만든 후 이벤트를 조회합니다. 다중 JOIN으로 같은 이벤트를 중복 반환하지 않습니다.

**마이그레이션 M1 — 조회 인덱스 초안 전문**

새 상태 컬럼이나 금액 집계 테이블은 만들지 않습니다.

```sql
BEGIN;

CREATE INDEX payments_live_invoice_amount
  ON ems.payments (organization_id, invoice_id)
  INCLUDE (amount)
  WHERE voided_at IS NULL;

CREATE INDEX quotes_client_updated
  ON ems.quotes (organization_id, client_id, updated_at DESC, id);

CREATE INDEX quotes_request_lookup
  ON ems.quotes (organization_id, request_id)
  WHERE request_id IS NOT NULL;

CREATE INDEX invoices_client_updated

CREATE INDEX visits_request_state
  ON ems.visits (organization_id, request_id, type, status)
  WHERE request_id IS NOT NULL;

CREATE INDEX visits_job_state
  ON ems.visits (organization_id, job_id, status)
  WHERE job_id IS NOT NULL;

CREATE INDEX expenses_org_date
  ON ems.expenses
```

인덱스 효과는 아직 측정하지 않았습니다. 팀장은 로컬 테스트 데이터로 실행 계획을 확인하고 중복·불필요 인덱스를 제거한 뒤 적용해야 합니다.

**마이그레이션 M2 — 안전한 활동 요약·감사 불변성 초안 전문**

원본 감사 테이블의 supervisor SELECT 정책을 추가하지 않습니다. 새 요약에는 JSON payload가 없습니다.

```sql
BEGIN;

CREATE FUNCTION ems.can_read_activity_summary(
  org uuid,
  kind text,
  entity uuid
)
RETURNS boolean
LANGUAGE sql
STABLE
SECURITY INVOKER
SET search_path = ''
AS $$
  SELECT ems.is_member(org) AND (
    ems.is_admin(org)
    OR CASE kind
      WHEN 'client' THEN EXISTS (
        SELECT 1 FROM ems.clients c
        WHERE c.organization_id = org AND c.id = entity
      )
      WHEN 'property' THEN EXISTS (
        SELECT 1 FROM ems.properties p
        WHERE p.organization_id = org AND p.id = entity
      )
      WHEN 'request' THEN EXISTS (
        SELECT 1 FROM ems.requests r
        WHERE r.organization_id = org AND r.id = entity
      )
      WHEN 'job' THEN ems.can_job(org, entity)
      WHEN 'visit' THEN ems.can_visit(org, entity)
      WHEN 'expense' THEN EXISTS (
        SELECT 1 FROM ems.expenses e
        WHERE e.organization_id = org
          AND e.id = entity
          AND e.user_id = auth.uid()
      )
      WHEN 'time_entry' THEN EXISTS (
        SELECT 1 FROM ems.time_entries t
        WHERE t.organization_id = org
          AND t.id = entity
          AND t.user_id = auth.uid()
      )
      ELSE false
    END
  );
$$;

REVOKE ALL ON FUNCTION
  ems.can_read_activity_summary(uuid, text, uuid)
  FROM PUBLIC, anon;

GRANT EXECUTE ON FUNCTION
  ems.can_read_activity_summary(uuid, text, uuid)
  TO authenticated;

CREATE TABLE ems.activity_summaries (
  id uuid PRIMARY KEY,
  organization_id uuid NOT NULL REFERENCES ems.organizations(id),
  actor_id uuid NOT NULL,
  entity_type text NOT NULL CHECK (
    entity_type IN (
      'client', 'property', 'request', 'job',
      'visit', 'expense', 'time_entry'
    )
  ),
  entity_id uuid NOT NULL,
  action text NOT NULL CHECK (
    action IN (
      'created', 'updated', 'archived', 'restored',
      'status_changed', 'submitted', 'approved',
      'rejected', 'reopened', 'timer_started', 'timer_stopped'
    )
  ),
  changed_fields text[] NOT NULL DEFAULT '{}',
  version integer NOT NULL DEFAULT 1 CHECK (version = 1),
  created_at timestamptz NOT NULL,
  updated_at timestamptz NOT NULL,
  UNIQUE (organization_id, id),
  FOREIGN KEY (organization_id, id)
    REFERENCES ems.activity_events (organization_id, id),
  FOREIGN KEY (organization_id, actor_id)
    REFERENCES ems.memberships (organization_id, user_id),
  CHECK (
    changed_fields <@ ARRAY[
      'displayName', 'contact', 'site', 'title', 'description',
      'status', 'schedule', 'assignees', 'notes', 'category',
      'amount', 'job', 'duration', 'receipt'
    ]::text[]
  )
);

ALTER TABLE ems.activity_summaries ENABLE ROW LEVEL SECURITY;

REVOKE ALL ON ems.activity_summaries
  FROM PUBLIC, anon, authenticated;

GRANT SELECT, INSERT ON ems.activity_summaries TO authenticated;

CREATE POLICY activity_summary_read
  ON ems.activity_summaries
  FOR SELECT TO authenticated
  USING (
    ems.can_read_activity_summary(
      organization_id, entity_type, entity_id
    )
  );

CREATE POLICY activity_summary_insert
  ON ems.activity_summaries
  FOR INSERT TO authenticated
  WITH CHECK (
    actor_id = auth.uid()
    AND ems.can_read_activity_summary(
      organization_id, entity_type, entity_id
    )
  );

CREATE INDEX activity_summary_entity_cursor
  ON ems.activity_summaries
  (organization_id, entity_type, entity_id, created_at DESC, id DESC);

REVOKE UPDATE, DELETE ON ems.activity_events FROM authenticated;

WITH normalized AS (
  SELECT
    id,
    organization_id,
    actor_id,
    CASE entity_type
      WHEN 'clients' THEN 'client'
      WHEN 'properties' THEN 'property'
      WHEN 'requests' THEN 'request'
      WHEN 'jobs' THEN 'job'
      WHEN 'visits' THEN 'visit'
      WHEN 'expenses' THEN 'expense'
      WHEN 'time_entries' THEN 'time_entry'
      WHEN 'timesheet' THEN 'time_entry'
      ELSE entity_type
    END AS entity_type,
    entity_id,
    CASE
      WHEN entity_type IN ('job', 'jobs')
        AND action = 'converted' THEN 'created'
      ELSE action
    END AS action,
    created_at
  FROM ems.activity_events
)
INSERT INTO ems.activity_summaries (
  id, organization_id, actor_id, entity_type,
  entity_id, action, changed_fields, created_at, updated_at
)
SELECT
  id, organization_id, actor_id, entity_type,
  entity_id, action, '{}'::text[], created_at, created_at
FROM normalized
WHERE entity_type IN (
  'client', 'property', 'request', 'job',
  'visit', 'expense', 'time_entry'
)
AND action IN (
  'created', 'updated', 'archived', 'restored',
  'status_changed', 'submitted', 'approved',
  'rejected', 'reopened', 'timer_started', 'timer_stopped'
)
ON CONFLICT (id) DO NOTHING;

COMMIT;
```

운영 연결 조건:

- `recordActivity`는 위 허용 대상에만 요약을 생성합니다. Job 전환은 요약에서 `created`로 표현하여 숨겨진 견적 ID를 노출하지 않습니다.
- `changed_fields`에는 값이 아닌 정해진 필드명만 넣습니다. `amount`는 본인 비용 이벤트에만 사용합니다.
- 과거 backfill에는 변경 필드를 추정해서 넣지 않습니다.
- 마이그레이션과 새 writer 사이에 생성된 이벤트가 누락되지 않도록, writer 전환 후 같은 `INSERT … ON CONFLICT DO NOTHING` backfill을 다시 수행하는 배포 순서를 준비합니다.
- `ems`를 Data API에 새로 노출하지 않습니다.

**마이그레이션 M3 — supervisor 상태 전이 보호 초안 전문**

기존 수정 열 제한을 유지하면서 상태 역전이·보관 Job 변경을 차단합니다. admin의 상세 전이 규칙은 도메인 서비스가 검사합니다.

```sql
BEGIN;

CREATE OR REPLACE FUNCTION ems.guard_supervisor_status()
RETURNS trigger
LANGUAGE plpgsql
SET search_path = ''
AS $$
DECLARE
  allowed text[] := ARRAY['status', 'version', 'updated_at'];
BEGIN
  IF ems.is_admin(OLD.organization_id) THEN
    RETURN NEW;
  END IF;

  IF TG_TABLE_NAME = 'jobs' THEN
    allowed := allowed || ARRAY['completed_at'];

    IF OLD.archived_at IS NOT NULL THEN
      RAISE EXCEPTION 'Archived jobs cannot be changed by supervisors'
        USING ERRCODE = '42501';
    END IF;
  END IF;

  IF (to_jsonb(NEW) - allowed)
      IS DISTINCT FROM (to_jsonb(OLD) - allowed) THEN
    RAISE EXCEPTION
      'Supervisors can change assigned record status only'
      USING ERRCODE = '42501';
  END IF;

  IF NEW.status IS DISTINCT FROM OLD.status THEN
    IF OLD.status IN ('completed', 'cancelled')
       OR NEW.status NOT IN ('in_progress', 'completed') THEN
      RAISE EXCEPTION 'This status transition requires an administrator'
        USING ERRCODE = '42501';
    END IF;
  END IF;

  IF TG_TABLE_NAME = 'jobs' THEN
    IF NEW.status = 'completed' THEN
      NEW.completed_at :=
        coalesce(OLD.completed_at, statement_timestamp());
    ELSE
      NEW.completed_at := NULL;
    END IF;
  END IF;

  RETURN NEW;
END;
$$;

REVOKE ALL ON FUNCTION ems.guard_supervisor_status()
  FROM PUBLIC, anon;

COMMIT;
```

마지막으로 작업 환경 문서 정리가 필요합니다. 실제 읽기 확인 결과 저장소 루트는 요청 경로와 같지만, 현재 브랜치는 **`jobber-ui-ux-overhaul`**입니다. 요청의 `sailfish` 브랜치 표기와 기존 문서의 “git 저장소가 아니다” 설명은 현재 환경과 다릅니다. 진행 중인 UI·lockfile 변경도 존재하며 건드리지 않았습니다.

이번 분석에서 검증하지 않은 것은 실행 시 재현, 실제 DB 정책·데이터 상태, SQL 실행 계획, 마이그레이션 적용 결과입니다. 위 완료 조건과 검증 명령은 후속 구현을 위한 기준입니다.
